# 🧠 Module 4 Quiz: Testing Strategies in Decoupled Architectures

🧪 **Goal:** Assess the ability to design a layered test strategy: domain in isolation, adapters through integration tests and the whole system end to end.

---

**1.** In a Test Pyramid applied to Hexagonal Architecture, where should most tests be concentrated?

a) Unit tests of the domain and application core  
b) Integration tests of driven adapters, since most bugs appear there  
c) End-to-end tests, since they validate real user behavior  
d) Contract tests, since they replace integration tests  

<details>
  <summary>Solution</summary>

- a
- The core is framework-free, so its tests are fast, stable and cheap. They form the wide base of the pyramid.
</details>

---

**2.** What makes it possible to test the application core in isolation?

a) The domain uses an in-memory database by default  
b) Domain classes are registered as beans in a test-specific DI context  
c) The core depends only on ports, so adapters can be replaced  
d) The domain uses static methods that need no instantiation  

<details>
  <summary>Solution</summary>

- c
- Dependency inversion lets you replace adapters with test doubles. Domain entities don't even need those doubles.
</details>

---

**3.** You are unit testing a use case that saves and later reads orders through an `OrderRepository` port. Which test double fits best?

a) A mock that verifies `save()` was called exactly once  
b) A fake in-memory repository  
c) A stub that always returns the same predefined order  
d) The real PostgreSQL adapter with an embedded database  

<details>
  <summary>Solution</summary>

- b
- A fake has simplified working behavior, so it supports save-then-read flows and tests state rather than implementation details.
</details>

---

**4.** What is the main difference between a stub and a mock?

a) Stubs are handwritten; mocks are generated by frameworks  
b) Stubs are for integration tests; mocks are for unit tests  
c) Stubs have simplified working logic; mocks return predefined values  
d) Stubs provide canned answers; mocks verify expected interactions  

<details>
  <summary>Solution</summary>

- d
- Stubs support state verification and mocks support behavior verification. Option c confuses stubs with fakes.
</details>

---

**5.** When is using a mock (interaction verification) most justified?

a) To check the result of a domain calculation  
b) To replace every collaborator of the class under test, ensuring full isolation  
c) To verify an outgoing side effect, like sending a notification through a driven port  
d) To verify which internal methods an entity calls on itself  

<details>
  <summary>Solution</summary>

- c
- When the observable outcome *is* the interaction, verifying it is appropriate. Overusing mocks (b, d) couples tests to implementation.
</details>

---

**6.** How should a driven adapter such as a SQL repository be tested?

a) With integration tests against the same database engine used in production  
b) With unit tests using H2 in-memory database instead of PostgreSQL  
c) With unit tests using a mocked JDBC connection or `EntityManager`  
d) Only indirectly, through end-to-end tests  

<details>
  <summary>Solution</summary>

- a
- The adapter's risk lies in queries, mapping and DB behavior. H2 differs in SQL dialect and features, and mocks validate nothing real.
</details>

---

**7.** What is the main benefit of tools like Testcontainers?

a) They make integration tests as fast as unit tests  
b) They remove the need for test doubles in unit tests  
c) They provide a shared, long-lived test database for the whole team  
d) They provide disposable, reproducible real dependencies for each test run  

<details>
  <summary>Solution</summary>

- d
- Each run gets isolated real services (DB, broker…). Shared environments (c) are exactly what causes flaky tests.
</details>

---

**8.** How should a driving adapter like a REST controller be tested?

a) Only through end-to-end tests with the real database  
b) Testing HTTP mapping, validation and status codes, with the driving port replaced by a test double  
c) Calling controller methods directly as plain unit tests, skipping the HTTP layer  
d) Testing the whole use case and domain logic through the controller  

<details>
  <summary>Solution</summary>

- b
- The controller translates HTTP. Option c misses routing, serialization and status codes, and d duplicates domain tests.
</details>

---

**9.** What problem does contract testing primarily solve?

a) Ensuring each service has enough integration test coverage  
b) Validating that the API documentation is up to date  
c) Verifying consumer and provider agree on an API without deploying them together  
d) Replacing the integration tests of driven adapters  

<details>
  <summary>Solution</summary>

- c
- Contract tests catch breaking changes early and cheaply, avoiding slow cross-service end-to-end tests.
</details>

---

**10.** In consumer-driven contract testing (e.g., Pact), who defines the contract?

a) The consumer, based on what it actually uses  
b) The provider, by publishing its full API specification  
c) Both teams, in a joint design meeting  
d) The API gateway, from observed traffic  

<details>
  <summary>Solution</summary>

- a
- Consumers state their expectations, and the provider verifies it meets all of them. Option b describes provider-driven contracts.
</details>

---

**11.** What is the role of end-to-end tests in a hexagonal system?

a) The main safety net, covering every business rule  
b) Replacing contract tests between services  
c) Running the system with test doubles for all adapters to gain speed  
d) Few tests covering critical journeys through all real adapters  

<details>
  <summary>Solution</summary>

- d
- They are slow and brittle, so they sit at the top of the pyramid and check that the wiring works.
</details>

---

**12.** Where should transaction boundaries typically be defined?

a) Inside domain entities, around each state-changing method  
b) At the Application Service (use case) level  
c) In each repository method separately  
d) In the driving adapter, around the call to the port  

<details>
  <summary>Solution</summary>

- b
- A use case is a unit of work. Option c breaks atomicity across several calls, and d puts a business decision in infrastructure.
</details>

---

**13.** What is a common pitfall of integration tests that roll back each test's transaction?

a) They may hide errors that only appear on commit or flush  
b) They leave test data behind, making tests depend on each other  
c) They can only be used with in-memory databases, not real ones  
d) They make results nondeterministic due to rollback ordering  

<details>
  <summary>Solution</summary>

- a
- Constraint violations may never fire. Also, the open test transaction keeps the persistence context alive, hiding lazy-loading errors.
</details>

---

**14.** How should cross-cutting concerns like security and logging be handled to keep the core testable?

a) Checking roles in each use case with `if (user.isAdmin())` statements  
b) Adding authorization checks inside domain entity methods  
c) Applying them around ports via decorators, middleware or aspects  
d) Delegating all authorization to database row-level permissions  

<details>
  <summary>Solution</summary>

- c
- They stay outside the core and are tested separately. Business-specific rules (e.g., "only the owner can cancel") may still belong to the domain.
</details>

---

**15.** What does the guideline "don't mock what you don't own" recommend?

a) Never use test doubles for any external dependency  
b) Mock third-party SDK classes directly, since they are stable  
c) Use the real third-party service in unit tests  
d) Wrap third-party libraries behind your own port and mock that port  

<details>
  <summary>Solution</summary>

- d
- Mocking vendor APIs encodes assumptions that may be wrong. The adapter's real behavior is verified with integration tests.
</details>
