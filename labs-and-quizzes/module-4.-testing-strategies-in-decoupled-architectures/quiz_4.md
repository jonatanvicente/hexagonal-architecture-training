# 🧠 Module 4 Quiz: Testing Strategies in Decoupled Architectures

**1.** In a Test Pyramid applied to Hexagonal Architecture, where should most tests be concentrated?

a) End-to-end tests through the UI   
b) Unit tests of the domain and application core  
c) Integration tests of the database adapters  
d) Contract tests between services  

<details>
  <summary>Solution</summary>
- b
- The domain is pure and framework-free, so its tests are fast, stable and cheap. They form the wide base of the pyramid.
</details>

---

**2.** What makes it possible to unit test the domain in complete isolation in Hexagonal Architecture?

a) The domain uses an in-memory database by default  
b) The domain is annotated with testing framework annotations  
c) The domain depends only on ports (abstractions), not on infrastructure  
d) The domain is deployed in a separate container  

<details>
  <summary>Solution</summary>
- c
- Dependency inversion means the core only knows interfaces (ports). Adapters can be replaced by test doubles or omitted entirely.
</details>

---

**3.** You are unit testing a use case that saves and later reads orders through an `OrderRepository` port. Which test double is usually the best fit?

a) A fake in-memory repository  
b) A mock that verifies `save()` was called exactly once  
c) The real PostgreSQL adapter  
d) A dummy object that throws on any call  

<details>
  <summary>Solution</summary>
- a
- A fake has real (simplified) behavior, so it supports save-then-read flows and tests state rather than implementation details.
</details>

---

**4.** What is the main difference between a stub and a mock?

a) Stubs are generated by frameworks; mocks are handwritten  
b) Stubs are used for integration tests; mocks only for unit tests  
c) Stubs contain real business logic; mocks do not  
d) Stubs provide canned answers; mocks verify expected interactions  

<details>
  <summary>Solution</summary>
- d
- Stubs support state-based testing by returning predefined data. Mocks support behavior verification by asserting how they were called.
</details>

---

**5.** When is using a mock (interaction verification) most justified?

a) To check the value returned by a domain calculation  
b) To verify that an outgoing side effect happened, like sending a notification through a port  
c) To replace every collaborator in every test  
d) To test private methods of an entity  

<details>
  <summary>Solution</summary>
- b
- When the observable outcome *is* the interaction (e.g., an email sent), verifying the call on the output port is appropriate. Overusing mocks couples tests to implementation.
</details>

---

**6.** How should a secondary (driven) adapter such as a SQL repository be tested?

a) With unit tests using a mocked JDBC driver  
b) Only indirectly through end-to-end tests  
c) With integration tests against a real database instance  
d) It doesn't need tests because it has no business logic  

<details>
  <summary>Solution</summary>
- c
- The adapter's risk lies in mapping, queries and DB behavior. Only a real database (e.g., via Testcontainers) validates that reliably.
</details>

---

**7.** What is the main benefit of tools like Testcontainers for controlled test environments?

a) They replace the need for unit tests  
b) They make tests run faster than in-memory tests  
c) They provide disposable, reproducible real dependencies for each test run  
d) They automatically generate test data  

<details>
  <summary>Solution</summary>
- c
- They spin up real services (DB, broker, etc.) in isolated containers, avoiding shared, unstable environments and "works on my machine" issues.
</details>

---

**8.** How should a primary (driving) adapter like a REST controller be tested?

a) By calling the domain entities directly  
b) By testing HTTP mapping, validation and status codes, with the input port replaced by a test double  
c) Only through full end-to-end tests with a real database  
d) By mocking the HTTP framework internals  

<details>
  <summary>Solution</summary>
- b
- The controller's responsibility is translating HTTP to use-case calls. Doubling the input port isolates that translation logic.
</details>

---

**9.** What problem does contract testing primarily solve?

a) Verifying that consumer and provider agree on an API without running both together  
b) Measuring code coverage across microservices  
c) Replacing all integration tests of adapters  
d) Testing database schema migrations  

<details>
  <summary>Solution</summary>
- a
- Contract tests catch breaking API changes early and cheaply, avoiding slow and fragile cross-service e2e tests.
</details>

---

**10.** In consumer-driven contract testing (e.g., Pact), who defines the contract?

a) The provider team  
b) An API gateway  
c) A shared QA team  
d) The consumer, based on what it actually uses  

<details>
  <summary>Solution</summary>
- d
- Consumers state their expectations; the provider verifies it satisfies all of them, so it knows which changes are safe.
</details>

---

**11.** Which statement best describes the role of end-to-end tests in a hexagonal system?

a) Few tests covering critical user journeys through all real adapters  
b) The main safety net, covering every business rule  
c) Tests that replace contract testing between services  
d) Tests that should mock all adapters for speed  

<details>
  <summary>Solution</summary>
- a
- E2E tests are slow and brittle, so they sit at the top of the pyramid and validate that the wiring works for key scenarios.
</details>

---

**12.** Where should transaction boundaries typically be defined in Hexagonal Architecture?

a) Inside domain entities  
b) At the application service / use case level  
c) In each repository method separately  
d) In the REST controller  

<details>
  <summary>Solution</summary>
- b
- A use case represents a unit of work. Defining the transaction there keeps the domain clean and ensures all its changes commit or roll back together.
</details>

---

**13.** What is a common pitfall of integration tests that automatically roll back each test's transaction?

a) They run too slowly to be useful  
b) They cannot insert test data  
c) They require a production database  
d) They may hide errors that only appear on commit/flush, such as constraint violations or lazy-loading issues  

<details>
  <summary>Solution</summary>
- d
- If the transaction never commits, the DB may not execute deferred constraints or flushes, giving false confidence.
</details>

---

**14.** How should cross-cutting concerns like security and logging be handled to keep the domain testable?

a) Applied around ports via decorators, middleware or aspects, outside the domain  
b) Embedded directly in every entity method  
c) Implemented inside database triggers  
d) Ignored in tests since they are infrastructure  

<details>
  <summary>Solution</summary>
- a
- Keeping them outside the core avoids polluting domain logic. They can be tested separately (e.g., authorization tests on adapters or decorators).
</details>

---

**15.** What does the guideline "don't mock what you don't own" recommend?

a) Never use test doubles for external services  
b) Only mock classes from your own domain entities  
c) Wrap third-party libraries behind your own port/adapter and mock the port, testing the adapter with integration tests  
d) Always use the real third-party service in unit tests  

<details>
  <summary>Solution</summary>
- c
- Mocking third-party APIs encodes assumptions that may be wrong. Mocking your own port is safe, and the real behavior is verified in the adapter's integration tests.
</details>
